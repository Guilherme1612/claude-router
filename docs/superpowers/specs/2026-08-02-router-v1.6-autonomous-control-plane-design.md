# Router v1.6 Autonomous Control Plane Design

**Date:** 2026-08-02  
**Status:** Approved design; pending written-spec review  
**Runtimes:** Claude Code and Codex  
**Architecture:** Structured control plane with native host dispatch adapters  
**Autonomy:** Project-goal leases with guarded automatic execution

## Purpose

Evolve the existing Router-build from a fast framework-neutral recommendation
hook into a fast framework-neutral autonomous control plane. Router must
understand what the user wants, whether execution is authorized, when acting is
better than asking, which installed public or private capabilities best fit,
how to execute with proportionate skills/commands/agents/tools, and how to
preserve truthful context across sessions.

The website audit in `docs/audits/coffee-router-system-audit.md` is evidence for
the design, not the feature scope. v1.6 is a general router milestone and must
not privilege GSD, website work, or any named workflow framework.

## Goals

- Preserve the current compiled, deterministic, fail-open hot path.
- Add real framework-neutral execution policies and native runtime dispatch.
- Distinguish advice, inspection, one-turn action, and persistent autonomous
  goals, including quotations, examples, negations, and policy discussion.
- Persist scoped project-goal autonomy across compaction and runtime restarts.
- Emit a compact truthful startup briefing for previously observed projects.
- Stay silent on first-ever Router visits with no meaningful continuity state.
- Resolve semantic actions against every compatible installed public, private,
  proprietary, plugin, service, and native capability.
- Improve the canonical manifest and semantic relationship mapping so unknown
  systems participate without framework-specific code.
- Select execution strategies from task/project complexity, dependencies,
  parallelism, specialist value, coordination cost, risk, and verification
  needs rather than fixed agent limits.
- Record recommendation-to-outcome evidence, actual substitutions, corrections,
  permissions, failures, and resource cost without a composite quality score.
- Permit safe local mapping evolution only through deterministic evidence,
  shadow comparison, canaries, and atomic rollback.
- Maintain Claude/Codex parity without pretending the runtimes expose identical
  startup, dispatch, expansion, or outcome hooks.

## Non-Goals

- No independent autonomous execution daemon.
- No LLM, API, network, filesystem scan, hashing, or learning on startup or
  prompt hot paths.
- No privileged routing for GSD, GStack, Superpowers, or another named system.
- No automatic sharing of private/proprietary capability data.
- No composite Router quality score.
- No automatic push, PR creation, deployment, publication, credentials use, or
  destructive/difficult-to-recover action.
- No silent permission expansion through learning.
- No automatic installation of missing capabilities.

## Design Principles

1. **Semantic action before framework name.** Router chooses what must happen,
   then resolves how the local installation can do it.
2. **Authority is separate from confidence.** Route confidence never grants
   permission to execute.
3. **Safety and correctness are hard constraints.** Required outcome quality
   comes next; total expected cost is optimized only inside those constraints.
4. **The host remains the execution boundary.** Router coordinates native
   runtime mechanisms rather than duplicating coding-agent and permission
   systems.
5. **Continuity is evidence-backed.** Startup summaries report meaningful
   outcomes, not the last tool call, and never invent missing state.
6. **Learning is local-first and reversible.** Safe improvements may promote
   automatically; uncertainty, trade-offs, privacy, or risk cause shadowing or
   a user question.
7. **Raw evidence over vanity metrics.** Users can audit behavior without a
   single score hiding trade-offs or failures.

## Architecture

```text
                         BACKGROUND CONTROL PLANE
 Installed capabilities ──→ Manifest vNext ──→ Semantic relationship mapping
        ▲                                             │
        │                                             ▼
 Runtime/project events ←── outcome observer ←── candidate compiler
        │                                             │
        │                                  validate/canary/activate/rollback
        │                                             ▼
        └──────────────────────────── immutable compiled state
                                                      │
                              STARTUP/PROMPT DATA PLANE
                                                      ▼
 prompt or startup → intent/authority/risk → route/action policy → host adapter
                                                               │
                                                               ▼
                                              native skill/command/agent/tool
                                                               │
                                                               ▼
                                                   execution receipt/checkpoint
```

### Compiled data plane

Startup and prompt hooks read small validated records containing project
continuity, the active autonomy lease, semantic route, resolved local
capability, risk, resource budget, and action policy. They do no discovery,
mapping, learning, or external I/O.

### Background control plane

The existing registry, watcher, adapters, mapping, health, observer, activation,
and rollback components are extended rather than replaced. The control plane
incrementally discovers capabilities, builds semantic relationships, attributes
outcomes, prepares candidates, validates them, and atomically publishes bounded
runtime/project views.

### Native host dispatch adapters

Claude Code and Codex adapters translate the same structured action policy into
the runtime's native invocation mechanisms. The adapter may invoke a skill,
command, agent, tool, plugin, connector, service, proprietary integration, or a
validated composition. The host's permission system remains authoritative.

Phase 1 must prove this boundary in both runtimes before later phases rely on
it. A model-readable recommendation alone is not accepted as proof of dispatch.

## Framework-Neutral Semantic Actions

Router represents work using actions such as:

- explore or recover context;
- define requirements or resolve an ambiguity;
- plan work;
- execute the next unblocked work unit;
- inspect or diagnose a failure;
- verify or test an outcome;
- review quality, safety, or integration;
- resume interrupted work;
- create a checkpoint or local commit;
- prepare release or publication while respecting confirmation boundaries.

Semantic actions are extensible. A capability may declare a new action contract
without requiring its framework name to be added to Router source code.

## Core Records

### Project continuity

```yaml
project_identity: stable repository/worktree identity
last_meaningful_action: completed or interrupted outcome summary
active_goal: goal identity and bounded description, or null
blockers: structured current blockers
recommended_next_action: semantic action contract, or null
evidence_refs: bounded authoritative references
freshness: timestamp, generation, and source fingerprint
```

Continuity is created only after Router observes meaningful work. Git history
alone does not create a first-visit startup message. Imported valid Router state
may establish continuity immediately.

### Project-goal autonomy lease

```yaml
goal: authorized outcome and scope
authority_source: explicit prompt or explicit Router command
status: active | completed | blocked | revoked | expired
allowed_effects: bounded safe local side-effect classes
confirmation_effects: external, privileged, destructive, or ambiguous classes
runtime_continuity: permitted Claude/Codex/session transitions
last_safe_checkpoint: receipt and artifact references
freshness: version, timestamp, and project fingerprint
```

Ordinary action requests authorize safe work for the current task. Phrases such
as “until finished,” “autonomously,” “do not stop,” “finish it,” or equivalent
unambiguously outcome-persistent instructions create a project-goal lease.

### Route decision

```yaml
task_domain: semantic domain, not framework name
intent_mode: advise | inspect | act | act_until_done
authority_source: explicit_prompt | active_lease | none
risk_class: normalized side-effect and permission class
required_contracts: semantic inputs, outputs, evidence, and transitions
resolved_capabilities: ordered local capabilities or composition
execution_strategy: sequential/parallel/delegated/native strategy
resource_budget: task-derived time/call/token/agent bounds
action_policy: auto_execute | validate_then_auto_execute | recommend_only | confirm | block
alternatives: rejected candidates and decisive reasons
```

### Execution receipt

```yaml
selected_capabilities: Router decision
actual_invocations: skills, commands, agents, tools, services, compositions
substitutions: replacements and reasons
start_state: authoritative checkpoint
end_state: completed | partial | failed | blocked | cancelled
outcome_evidence: artifacts, checks, and user acceptance/correction
cost: wall time, cached/uncached tokens, calls, retries, failures, coordination
permissions: requested, allowed, confirmed, denied
continuity_update: next meaningful project state
```

Receipts are bounded summaries with references to detailed traces. Large logs
never enter compiled startup/prompt state.

## Capability Manifest vNext

Every capability record must include:

- stable identity, provider, ownership, runtime, scope, version, fingerprint,
  and provenance;
- public, private, proprietary, plugin, service, or native classification;
- invocation type, entrypoint, argument contract, environment, and runtime
  adapter details;
- semantic actions, accepted inputs, produced outputs/artifacts, preconditions,
  postconditions, and completion evidence;
- required tools, agents, permissions, credentials, dependencies, and services;
- side effects, reversibility, confirmation requirements, and risk class;
- supported task domains, project contexts, and worktree/runtime constraints;
- observed latency, token/tool intensity, coordination traits, availability,
  failures, and compatibility;
- export/redaction policy for private information;
- lifecycle state: discovered, mapped, shadowed, active, degraded, quarantined,
  removed.

Capabilities include public/private workflow frameworks, organization-specific
orchestration, proprietary commands/CLIs, skills and bundles, custom agents and
orchestrators, plugins, MCP servers/tools, apps/connectors, hooks/extensions,
local scripts/services, internal APIs, native runtime tools, and safe
compositions of them.

Unknown private capabilities may enter through declared contracts,
deterministic inspection, or guarded background inference and shadow
observation. Unknown names never reduce eligibility when the semantic contract
is otherwise valid.

## Adaptive Semantic Mapping

The local mapping is a relationship graph whose edges include:

```text
satisfies        requires          produces
composes_with    substitutes_for   conflicts_with
supersedes       unavailable_when  scoped_to
```

Resolution supports equivalent frameworks, multi-capability compositions,
runtime/project/worktree overlays, positive and negative conditions,
dependencies, permissions, declared/observed/inferred evidence, ignored and
corrected routes, manifest invalidation, and last-known-good compilation.

Strict lint blocks ambiguous ties, identity collisions, stale targets, missing
dependencies, unsafe composition, scope leakage, incompatible outputs, and
unresolvable invocation contracts.

## Intent, Authority, and Meta-Language

Router classifies each interaction as:

- `advise`: explanation or recommendation without mutation;
- `inspect`: read-only investigation;
- `act`: execute the requested safe task;
- `act_until_done`: establish or continue a persistent lease.

Classification must distinguish real instructions from quotations, examples,
negations, hypotheticals, policy discussion, and retrospective audit text. For
example, “test different colors” is not automated-test generation, and
discussing the phrase “use subagents and fix this” does not authorize agent
dispatch.

## Autonomy and Safety Policy

With current-task authority or an active lease, Router may automatically read
and edit local files, run tests/builds/audits, invoke compatible local/private
capabilities, dispatch a proportionate execution strategy, substitute a failing
route, create local commits/checkpoints, and continue across compaction or
runtime restarts.

Router pauses before pushes, PRs, publication/deployment, external messages,
credentials/secrets/billing/privileged access, destructive or difficult-to-
recover operations, material scope expansion, subjective choices where asking
is likely to improve the outcome, conflicting evidence, or uncertain safety.

Corrupt, stale, incompatible, or foreign-project state cannot grant authority.
Confidence and historical success never widen permissions.

## Adaptive Execution Strategy

Agent count and capability composition are planning outputs, not fixed presets.
Router estimates:

- task and project complexity;
- dependency graph and genuine parallelism;
- specialist value and capability availability;
- coordination overhead;
- risk and verification requirements;
- runtime capacity;
- expected outcome quality and total cost.

Router selects the cheapest reliable strategy inside safety, correctness, and
quality constraints. It may substitute an underperforming route during an
active lease when authorization and risk remain unchanged. Material strategy
or scope changes require confirmation.

Every command passes mechanical runtime policy: availability, permission,
working-directory scope, required wrappers such as RTK where configured,
destructive-target validation, and bounded timeout/output expectations.

## Startup and Continuity Experience

Previously observed projects receive one compact message per runtime session
and project/worktree:

```text
Router
Last: <last meaningful completed or interrupted action>
Goal: <active goal and lease state>
Next: <framework-neutral semantic action>
Using: <best resolved local capability or composition>
Why: <one evidence-backed sentence>
Action: <resuming, waiting, blocked, or complete>
```

- First-ever Router visit or no meaningful continuity: silent.
- Active unfinished lease: brief, then resume safe work.
- Incomplete work without a lease: brief, then wait.
- Completed goal: brief completion and next recommendation, then wait.
- Blocked goal: identify the blocker and exact decision required.
- Stale/corrupt/mismatched state: never auto-resume; warn only when useful.

The recommendation is resolved from current project state and installed
capabilities. Detailed evidence, alternatives, costs, and rejected routes are
available through inspection commands rather than startup-token expansion.

Claude and Codex use native startup mechanisms where available. Any fallback
must be labeled truthfully and proven in the Phase 1 feasibility gate.

## Observability and Local Learning

Router records raw route evidence rather than a composite score:

- recommended, selected, invoked, ignored, rejected, substituted, blocked,
  completed, partial, and failed states;
- actual capability/agent/tool/command compositions;
- corrections, explicit acceptance, and causal outcome evidence;
- time, cached/uncached tokens, calls, retries, failures, and coordination cost;
- permission/safety decisions, artifacts, and verification references;
- predicted-versus-observed strategy differences;
- alternatives and decisive rejection reasons.

Learning is local per installation by default. Sanitized mapping export/import
is optional. Private capability data is never automatically shared.

Successful downstream work does not validate an ignored recommendation. The
observer attributes the selected route, replacement, outcome, and correction
separately.

Safe mapping changes may auto-promote only when they do not expand permission
or risk, pass deterministic correctness/safety/performance/compatibility gates,
have sufficient consistent local evidence, beat the active mapping without a
quality regression, pass shadow/canary comparison, and have atomic rollback.
Sparse evidence, trade-offs, subjective preference, opaque proprietary
behavior, or uncertain safety remains shadowed or asks the user.

## Performance Requirements

- Warm prompt routing p95 ≤25ms and p99 ≤50ms.
- Hard prompt release gate <100ms.
- Startup briefing p95 ≤50ms.
- Normal Router injection ≤120 tokens.
- Zero hot-path LLM/API/network calls, scanning, hashing, or learning.
- Bounded compiled-state reads only.
- Slow, stale, corrupt, or unavailable optional components fail open.
- Background work cannot delay startup or prompt submission.

## Error Handling

- Missing/stale mapping: use last-known-good compiled state or safely re-resolve.
- Unavailable capability: select the next compatible local candidate.
- Dispatch failure: receipt, checkpoint, then safe substitution when possible.
- Repeated failure or budget exhaustion: one evidence-backed replan, then block.
- Adapter incompatibility: disable autonomous dispatch for that runtime while
  preserving truthful recommendations.
- Corrupt continuity/lease: quarantine; never infer authority.
- Partial completion: retain completed dependencies and resume only unfinished
  work.
- Failed learned candidate: atomic last-known-good rollback.
- Observer integrity failure: allow otherwise-safe execution, but suspend
  learning and promotion.

## Cross-Runtime Feasibility Gate

Before building downstream autonomy, Phase 1 must demonstrate in Claude and
Codex:

1. Loading compiled project continuity at startup.
2. Emitting the same truthful compact briefing.
3. Automatically invoking one harmless local fixture under an active lease.
4. Capturing selected → invoked → completed evidence.
5. Pausing on an external/destructive fixture.
6. Meeting latency and token budgets.
7. Operating without an independent daemon or named-framework assumption.

Failure in either runtime blocks the architecture and requires adapter redesign.

## Validation Strategy

Validation covers:

- Claude/Codex startup and dispatch parity;
- GSD, GStack, Superpowers, private-framework fixtures, and native fallback;
- unknown proprietary capability discovery and mapping;
- quoted/example/negated/hypothetical discrimination;
- one-turn action versus persistent lease recognition;
- safe execution and confirmation boundaries;
- substitution, budget exhaustion, and rollback;
- complexity-aware agent/capability strategies;
- command-policy enforcement;
- causal outcome attribution and ignored/corrected route learning;
- new-project silence and existing-project briefing;
- compaction/restart continuity;
- stale/corrupt/foreign-project isolation;
- performance and injection-token gates;
- install, upgrade, repair, enable/disable, and uninstall lifecycle.

Final acceptance uses multiple unfamiliar workloads and at least one private
mock framework Router has never seen. Passing requires discovery, mapping,
invocation, observation, and safe improvement without framework-specific code.

## Milestone Phases

1. **Cross-Runtime Autonomous Dispatch Feasibility**
2. **Semantic Intent, Authority, Risk, and Meta-Language**
3. **Project-Goal Leases and Startup Continuity**
4. **Capability Manifest vNext**
5. **Adaptive Semantic Mapping and Relationship Engine**
6. **Native Dispatch and Adaptive Execution Strategy**
7. **Execution Receipts and Causal Outcome Attribution**
8. **Safe Local Evolution, Promotion, and Rollback**
9. **Efficiency, Adversarial Validation, and Release Lifecycle**

The order proves runtime feasibility first, establishes authority and
continuity, upgrades manifest and mapping before adaptive dispatch, then adds
outcome learning and release gates.

## Acceptance Criteria

1. A safe correction under an active lease invokes the fitting capability
   without another user command.
2. “Test several color/font options” does not route to automated-test
   generation.
3. “Audit Router-build using a website workload” does not route to UI polish.
4. Discussing autonomous phrases does not itself grant authority.
5. A small single-path correction uses no agents unless specialist value is
   evidenced; larger work selects agents from its dependency/cost model.
6. GSD, GStack, Superpowers, proprietary fixtures, and native tools resolve from
   semantic contracts without privileged source-code branches.
7. First-ever project visits are silent; valid continuing projects receive one
   truthful compact startup briefing.
8. Active leases resume safe work across supported restart/compaction paths;
   completed, blocked, or unauthorized work does not auto-run.
9. Every emitted route reaches an invoked, substituted, rejected, blocked, or
   failed state and an attributable outcome receipt.
10. Safe learned mappings pass shadow/canary gates and rollback automatically;
    permission/risk expansion never auto-promotes.
11. Both runtimes meet the startup, prompt latency, token, lifecycle, and
    failure-isolation requirements.
