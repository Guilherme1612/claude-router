# Router v1.8 Adaptive Semantic Routing and Continuity Design

**Status:** Approved architecture, implementation not started  
**Milestone:** v1.8  
**Runtimes:** Claude Code and Codex  
**Operating model:** Local-first, framework-neutral, capability-adaptive  
**Primary constraint:** More autonomous without adding prompt-path weight or weakening authority controls

## 1. Outcome

Router v1.8 makes each installed runtime understand what the user is trying to accomplish, select the least sufficient combination of locally available skills, agents, commands, and native tools, and prove that the selected capabilities were actually used correctly.

The system does not depend on users naming a capability or repeating a trigger phrase. A request such as “check the database relationships” may resolve to a graph or schema-inspection workflow when that is the best available local capability. A request such as “redesign this interface” may compose design-direction, UX-system, implementation, and visual-review capabilities without requiring the user to name any of them.

On entry, previously observed projects receive a compact, evidence-backed continuity message containing the last verified result, current state, and one likely next action. Automatic resumption occurs only under a valid explicit autonomy lease.

## 2. Design corrections

### 2.1 “100% mapped” means complete typed coverage

The target is not an explicit phrase table for every installed item. That would be slow, fragile, and impossible to keep portable.

For each active runtime, 100% means:

1. every discoverable local capability is represented in that runtime's normalized registry;
2. every registry record has a valid type and provenance;
3. every record is classified as routable, composable, direct-only, hook-owned, project-scoped, unavailable, invalid, or intentionally excluded;
4. every routable record has enough inferred or declared contract data to participate in semantic selection;
5. every selection resolves only to capabilities currently available in that runtime;
6. every uncovered or invalid record appears in deterministic audit output.

Claude uses Claude's discovered inventory and host adapter. Codex uses Codex's discovered inventory and host adapter. They share canonical semantics and workflow contracts, not copied runtime directories or identical capability counts.

### 2.2 Personal setups are fixtures and overlays

The product must not be built around the maintainer's `.claude`, `.codex`, skill names, plugin set, or directory layout.

The maintainer setup is used as one high-complexity integration fixture. Portable synthetic fixtures cover empty, minimal, common, conflicting, partially invalid, project-scoped, plugin-heavy, and cross-runtime installations. User preferences are stored in a local overlay keyed by semantic capability identity, with aliases only as hints.

### 2.3 Selection is semantic and workflow-first

Names and exact phrases may improve recall but cannot be the deciding contract. Selection follows:

`prompt -> intent -> desired outcome -> workflow requirements -> eligible local capabilities -> composition -> authority/risk policy -> execution -> receipt -> verification`

## 3. Existing architecture to extend

v1.8 extends the existing manifest builder, normalized registry, intent classifier, mode-map metadata, compiled prompt index, startup pointer/acknowledgement, autonomy leases, native runtime adapters, receipts, verification, and local learning.

It must not introduce a second router, a database, embeddings, a network service, or prompt-time inventory scanning. Discovery, normalization, inference, evaluation, and compilation remain off the prompt path. Prompt-time work reads bounded immutable artifacts and performs deterministic ranking and policy checks.

## 4. Capability contract

Each discovered item becomes a normalized capability record. Declared metadata wins; safe inference fills missing fields; unresolved ambiguity lowers eligibility rather than inventing authority.

Minimum contract:

```text
identity          stable semantic id plus runtime-local locator
runtime           claude | codex | compatible future adapter
kind              skill | agent | command | tool | hook | workflow
provenance        runtime, plugin, project, user, generated, or built-in
availability      present, loadable, enabled, and dependency state
intents           semantic actions the capability can satisfy
inputs            accepted subjects, artifacts, and preconditions
outputs           expected artifacts, mutations, or observations
effects           read, write, execute, network, publish, destructive
risk              bounded policy class
authority         advice, inspect, act-once, leased, owner-gated
composition       compatible roles, ordering, conflicts, exclusivity
cost              bounded latency/context/tool-call hints
quality           evidence requirements and known confidence
aliases           names and phrases used only as retrieval signals
source_hash       stale-artifact detection
```

Records that cannot safely execute may still support recommendation or explanation. Unknown effects, dependencies, or authority never become auto-executable through inference.

## 5. Semantic intent and workflow resolution

### 5.1 Intent representation

The classifier produces a bounded structured intent instead of a single label:

```text
goal              what outcome the user wants
subjects          code, database, UI, tests, release, docs, etc.
operations        inspect, explain, design, build, fix, verify, publish, etc.
constraints       speed, framework, style, privacy, named preferences
evidence_needed   inspection, tests, browser proof, receipt, review, etc.
execution_signal  hypothetical, advice, inspect, explicit act, continue lease
confidence        evidence-backed routing confidence
```

Negation, quotation, examples, hypothetical language, and “do not execute” remain non-execution signals. Capability names explicitly supplied by the user are constraints or preferences, not permission expansion.

### 5.2 Retrieval and ranking

Candidate retrieval combines bounded signals already available locally:

- declared and inferred capability intents;
- canonical workflow requirements;
- semantic aliases and descriptions;
- project context and artifact types;
- runtime availability and dependencies;
- user preference overlay;
- prior verified local outcomes;
- conflicts, risk, authority, and cost.

Ranking favors the least sufficient eligible set. A single capability wins when it covers the workflow. Composition is used only when distinct required roles remain uncovered.

No global composite quality score is introduced. Selection diagnostics expose separate dimensions such as intent fit, requirement coverage, availability, authority, risk, estimated cost, and evidence strength.

### 5.3 Composition

Canonical workflows define roles, not product names. Examples:

- data-relationship inspection: discover schema/context -> relationship analysis -> evidence summary;
- UI redesign: design direction -> UX/system constraints -> implementation -> visual/accessibility review;
- bug repair: reproduce -> diagnose root cause -> implement -> focused verification;
- release: readiness audit -> tests -> installed-runtime verification -> publish only with authority.

A local capability may satisfy multiple roles. The resolver must collapse redundant selections, obey ordering, reject conflicts, and cap the number of injected or invoked capabilities.

For a UI redesign on the maintainer's current setup, a local preference overlay may favor Impeccable for design direction and critique, taste-skill for distinctive implementation direction, and UI/UX Pro Max for system and UX guidance. Another installation may resolve the same roles to entirely different capabilities. Small UI tasks use only the required subset; substantial redesigns may use the full compatible bundle.

### 5.4 Fallback

If no eligible capability satisfies the workflow, Router returns the best safe native action, recommendation, or concise missing-capability explanation. It does not fabricate a command, invoke a disabled item, or silently substitute a higher-risk action.

## 6. Runtime projection and parity

A canonical registry model is projected separately into Claude and Codex artifacts:

```text
local runtime inventory
  -> normalized capability records
  -> canonical semantic identities and workflow roles
  -> runtime-specific eligibility and invocation locators
  -> bounded compiled index
  -> atomic activation
```

Parity tests compare semantics, workflow behavior, and classified coverage where equivalent capabilities exist. They do not require identical file paths, counts, commands, or host mechanics.

Runtime-native invocation remains adapter-owned. Claude capability selections never execute through Codex paths, and Codex selections never rely on Claude-only paths. Cross-runtime comparison is diagnostic, not an execution bridge.

## 7. Startup continuity digest

v1.8 extends the existing startup pointer and acknowledgement path.

For a previously observed project with meaningful evidence, startup may display:

```text
Last verified: verified_outcome — evidence_ref
Current: state_summary
Likely next: action — rationale
Resume: automatic only under lease lease_id; otherwise awaiting instruction
```

Rules:

- no message for a first visit or meaningless state;
- no claim based only on a plan, assistant prose, or an unverified receipt;
- stale pointers degrade to a refresh recommendation;
- exactly one primary next action;
- bounded size and no inventory scan at startup;
- acknowledgement prevents repeated display of unchanged state;
- project identity prevents continuity leaking across repositories;
- active valid leases may resume only actions inside their goal, risk, resource, and time bounds;
- publication, destructive actions, credentials, payments, and other owner gates remain blocked regardless of routing confidence.

The likely-next selector uses verified project state and workflow transitions. It is deterministic for the same compiled state; it is not a free-form autonomous planner on the startup path.

## 8. Preference overlays

Preferences are optional, local, and portable:

```text
semantic role -> preferred capability ids or aliases -> scope -> priority
```

Scopes are global user, runtime, project, and workflow. Narrower scopes win. Preferences may break ties or request a compatible bundle, but cannot bypass absence, incompatibility, authority, risk, or workflow requirements.

Aliases support renamed or relocated capabilities. Unresolved aliases produce an audit warning and do not block unrelated routing.

## 9. Evaluation laboratory

The repository gains a deterministic local evaluation mechanism that answers whether routing is becoming faster, more efficient, and more correct without depending on the maintainer's live installation.

### 9.1 Fixture matrix

Fixtures include:

- empty and minimal Claude/Codex homes;
- equivalent capabilities with different names and descriptions;
- prompts with paraphrases, misspellings, indirect intent, negation, quotation, and hypothetical language;
- one-capability and composed-workflow cases;
- unavailable, disabled, conflicting, stale, malicious, and missing-dependency capabilities;
- personal preference overlays separated from default behavior;
- startup states with verified, stale, absent, blocked, leased, and cross-project evidence;
- clean-install, upgrade, rollback, and uninstall lifecycle states.

The current `.claude` and `.codex` inventories are imported only into ignored/generated integration fixtures or sanitized snapshots. They are never required for the default suite.

### 9.2 Independent measurements

Each evaluation reports separate values:

- inventory discovery and typed-classification coverage;
- correct workflow and capability-set selection;
- unsafe or unavailable selection count;
- unnecessary capability and tool-call count;
- intent false-positive and false-negative cases;
- prompt-path p50/p95 latency and cold/warm startup latency;
- compiled artifact size and injected context bytes;
- execution receipt completeness;
- verification evidence satisfaction;
- installed-runtime parity and lifecycle results.

No single score hides regressions. A candidate fails when any mandatory safety, correctness, coverage, or performance threshold regresses beyond its explicit budget.

### 9.3 Behavioral proof

Tests must prove more than recommendation text:

1. the expected semantic workflow was selected;
2. the resolved capability set was locally eligible;
3. the correct runtime-native invocation identity was used when execution was authorized;
4. receipts link intent, route, action, capability, lease, and completion evidence;
5. required verification ran and matched the expected outcome;
6. learning or preference changes cannot activate until candidate calibration and atomic publication pass.

Golden cases are reviewed, versioned, and explainable. Property and mutation-style cases cover wording variation and safety boundaries without requiring an LLM or network.

## 10. Performance and weight budgets

v1.8 remains lightweight by construction:

- no new runtime dependency unless existing platform code cannot satisfy a measured requirement;
- no LLM, network, hashing sweep, filesystem scan, or learning on prompt/startup paths;
- bounded compiled index loaded once and invalidated by version/hash metadata;
- incremental rebuild for changed capability sources, with periodic full-equivalence checks;
- candidate caps before expensive ranking or composition;
- small fixed composition and context-injection limits;
- atomic artifact publication and last-known-good recovery;
- diagnostics and evaluation run explicitly or asynchronously outside user prompt latency.

Exact numeric budgets are established from the v1.7 baseline during milestone planning. Safety and correctness gates are absolute; performance budgets must compare the same fixture, machine class, runtime mode, and warm/cold condition.

## 11. Installation and adaptation

The existing installer lifecycle is extended rather than replaced.

Installation must:

1. detect supported runtimes and their actual local roots;
2. install only shared core plus detected runtime adapters;
3. discover capabilities without copying private content into the repository;
4. build runtime-specific registries and compiled indexes locally;
5. validate hooks, paths, permissions, and compatibility before activation;
6. preserve user-owned files and coexist with existing hooks/plugins;
7. record every owned mutation for upgrade, rollback, and uninstall;
8. run a smoke evaluation against generated minimal fixtures and the installed projection;
9. fail closed to the previous working activation.

Unsupported hosts remain recommendation-only until an explicit adapter contract and lifecycle tests exist.

## 12. Review and observability

Router exposes concise local diagnostics for:

- why a workflow and capability set were selected;
- which candidates were rejected and by which independent constraint;
- whether each registry item is mapped, inferred, direct-only, hook-owned, scoped, invalid, or excluded;
- whether compiled artifacts match source fingerprints;
- whether startup evidence is current and acknowledged;
- whether execution and verification receipts close the requested outcome;
- baseline-versus-candidate measurement deltas.

Raw prompts, private capability bodies, credentials, and user project content are not exported. Diagnostics use bounded identifiers, contract summaries, hashes where already required for integrity, and redacted evidence.

## 13. Failure handling

- Invalid capability metadata quarantines that record, not the whole registry, unless it violates activation integrity.
- Invalid compiled artifacts retain the last known good activation.
- Ambiguous low-confidence intent passes through or asks for clarification; it does not execute.
- Conflicting workflow capabilities resolve to the least risky sufficient set or stop with a concise conflict.
- Missing verification evidence leaves work incomplete even when a command exits successfully.
- Stalled native execution is bounded, observable, and recoverable through existing receipt controls.
- Learning cannot silently rewrite active routing.

## 14. Milestone acceptance

v1.8 is complete only when all of the following are evidenced:

1. Claude and Codex inventories each achieve 100% discovered-record classification under the typed coverage definition.
2. Semantic paraphrase tests select correct workflows without exact capability names.
3. Multi-capability composition selects the least sufficient compatible set and proves real use through receipts.
4. UI workflow fixtures demonstrate portable role-based composition, with the maintainer preference overlay tested separately.
5. Startup continuity displays truthful last/current/next state, stays quiet when appropriate, and resumes only under a valid lease.
6. Safety tests reject negated, hypothetical, unavailable, conflicting, stale, and unauthorized execution.
7. Baseline/candidate reports show independent routing, latency, context, tool-call, and verification measurements with no mandatory regression.
8. Clean install, upgrade, rollback, uninstall, and last-known-good recovery pass for both supported runtimes in isolated homes.
9. Installed Claude and Codex smoke tests prove the generated projections are active and host-native.
10. Documentation explains semantic coverage, preferences, diagnostics, testing, portability, and recovery without assuming the maintainer's setup.

## 15. Explicit non-goals

- Hardcoding the maintainer's installed capability list.
- Mapping every possible user sentence by hand.
- Making Claude and Codex inventories byte-for-byte identical.
- Automatically invoking every relevant skill or agent.
- Adding a remote telemetry service, embeddings store, daemon, dashboard, or LLM router.
- Treating routing confidence as execution authority.
- Replacing runtime-native adapters with cross-runtime shell delegation.
- Publishing to GitHub as part of this local design step.

## 16. Implementation boundary

This document defines the v1.8 product and acceptance contract. Milestone requirements, phases, implementation plans, code changes, generated runtime artifacts, and release publication follow only after this specification is reviewed and accepted.
