# Requirements: Claude Router v1.3

**Defined:** 2026-07-23
**Core Value:** The user can write the minimum useful prompt and still get the best available workflow automatically, with low token overhead, sub-100ms prompt routing, and no per-prompt external classifier.

## v1.3 Requirements

### Personalized Discovery and Reconciliation

- [x] **DISC-01**: Router discovers user- and project-scoped commands, skills, agents, hooks, MCP servers, tools, plugins, and instruction files from the actual `.claude` and `.codex` installations.
- [x] **DISC-02**: Router records each discovered capability's runtime, scope, source provenance, enabled state, invocation form, dependencies, and lifecycle role without relying on ecosystem-specific names.
- [x] **DISC-03**: Adding, editing, renaming, moving, disabling, removing, or replacing a capability updates the candidate registry and every affected relationship.
- [x] **DISC-04**: Incremental reconciliation and periodic authoritative reconciliation converge to the same byte-identical candidate map after missed, duplicated, coalesced, or reordered filesystem events.
- [x] **DISC-05**: Capability removal or dependency loss invalidates transitive aliases, equivalence edges, workflow edges, corrections, and compiled routes before activation.
- [x] **DISC-06**: Claude-versus-Codex capability gaps are identified by semantic category and local availability without treating either runtime or any framework as the default.
- [x] **DISC-07**: Unknown future capability types can be represented through adapter boundaries and normalized evidence without adding ecosystem conditionals to Router core.
- [x] **DISC-08**: Discovery canonicalizes paths, rejects scope escapes and unsafe symlinks, and treats capability-authored text as untrusted evidence rather than executable policy.

### Capability Contracts and Relationships

- [ ] **CONT-01**: Every discovered capability receives a normalized contract covering purpose, triggers, inputs, outputs, preconditions, dependencies, permissions, side effects, reversibility, risk, invocation kind, lifecycle role, scope, and workflow transitions.
- [ ] **CONT-02**: Every inferred contract field records its evidence, provenance, inference rule version, and confidence independently.
- [ ] **CONT-03**: Missing, conflicting, stale, or low-confidence dispatch-relevant fields remain `unknown` and make the capability recommendation-only.
- [ ] **CONT-04**: Optional local manifests can enrich or correct inferred fields without being required and without inventing capabilities absent from the authoritative installation.
- [ ] **CONT-05**: Manifest enrichment and user-approved corrections are schema-validated, versioned, inspectable, and bound to the exact capability identity and fingerprint.
- [ ] **CONT-06**: Renamed, replaced, or modified capabilities invalidate stale corrections unless exact lineage evidence permits safe carryover.
- [ ] **CONT-07**: Router classifies relationships as substitute, variant, prerequisite, composition, conflict, fallback, implementation, or alias instead of assuming equivalence from name similarity.
- [ ] **CONT-08**: Only contracts passing target-existence, invocation-shape, adapter, dependency-closure, permission, scope, and side-effect validation can become dispatch eligible.
- [ ] **CONT-09**: Users can inspect inferred contracts, evidence, confidence, rejected candidates, relationships, and correction paths without editing Router core.

### Intent Classification

- [x] **INT-01**: Router deterministically classifies prompts as execute, explain, hypothetical, quoted/example, negated, prohibited, preview, or ambiguous using a compiled local policy.
- [x] **INT-02**: Only an explicit positive execute classification can enter action selection; every other classification sets `dispatch_eligible: false`.
- [x] **INT-03**: Explanations, comparisons, questions, hypotheticals, quotations, code blocks, examples, negations, prohibitions, conditions, and ambiguous requests never invoke a capability.
- [x] **INT-04**: The newest explicit user instruction overrides stale conversational hints and recovered workflow state.
- [x] **INT-05**: Uncertain compatibility, intent, state, permissions, dependencies, or side effects produces abstention, one focused clarification, or a non-executing recommendation.
- [x] **INT-06**: Adversarial fixtures cover minimal pairs, nested quotations, mixed negation, corrections, conditional language, multilingual prompts, unsafe targets, and assertions that prohibited invocations did not occur.

### State-Aware Framework-Neutral Execution

- [x] **EXEC-01**: Router resolves natural-language actions against normalized contracts for the capabilities currently installed, never against hard-coded GSD, Gstack, or other framework command names.
- [x] **EXEC-02**: “Go to the next phase” discovers authoritative project state, identifies the unique valid next transition, and invokes the safest compatible installed capability.
- [x] **EXEC-03**: “There is a bug” or “debug this” selects the compatible installed debugging command, skill, agent, or tool according to contract, state, scope, and dependency health.
- [x] **EXEC-04**: “Create a phase about X” discovers the project’s current phase numbering and lifecycle state, then invokes the compatible installed phase-creation capability with the derived next number and supplied topic.
- [x] **EXEC-05**: Automatic dispatch requires fresh authoritative state, exactly one eligible transition, healthy dependencies, valid structured arguments, runtime permission, scope authorization, and all applicable safety gates.
- [x] **EXEC-06**: Ties, stale or contradictory state, terminal workflows, unresolved gaps, missing dependencies, material side effects, or human-required checkpoints prevent automatic dispatch.
- [x] **EXEC-07**: Destructive, external, privileged, ambiguous, or difficult-to-reverse actions require an approval distinct from execute intent.
- [x] **EXEC-08**: Approval is bound to the exact capability fingerprint, arguments, targets, effects, and proposal version; stale or mismatched approval fails closed.
- [x] **EXEC-09**: Router never elevates Claude or Codex permissions, bypasses sandbox/tool restrictions, treats discovery as authorization, or invokes lifecycle hooks as task tools.
- [x] **EXEC-10**: After completing work, Router continues to recommend the correct next locally available capability and provides a ready-to-use prompt without assuming a framework-specific command.

### Local Outcomes and Capability Health

- [x] **HLTH-01**: Background analysis stores no raw prompts, transcripts, secrets, arbitrary tool output, source documents, or unbounded arguments.
- [x] **HLTH-02**: No prompt data, capability metadata, telemetry, usage information, health evidence, or recommendation state leaves the local machine.
- [x] **HLTH-03**: The bounded outcome schema distinguishes selected, actually used, completed, corrected, retried, replaced, abandoned, overridden, and helpful reuse events.
- [x] **HLTH-04**: Outcome records use allowlisted fields, stable local identifiers, retention limits, decay windows, restrictive permissions, corruption checks, and bounded compaction.
- [x] **HLTH-05**: Users can inspect, reset, dispose of, and recover bounded health state without affecting authoritative capability definitions or the active routing map.
- [x] **HLTH-06**: Usefulness scoring considers opportunity exposure, completion, verification, correction, retry, replacement, abandonment, override, recency, reversibility, and confidence rather than frequency alone.
- [x] **HLTH-07**: Rare, recovery-oriented, incident-response, release, and migration capabilities are not classified as useless solely because they are infrequently invoked.
- [x] **HLTH-08**: Router identifies missing categories, missing dependencies, unmapped capabilities, stale capabilities, long-unused capabilities, exact duplicates, semantic overlaps, complementary compositions, and repeatedly ineffective selections.
- [x] **HLTH-09**: Router detects repeated multi-step workflows that are strong candidates for reusable skills or agents and distinguishes healthy repetition from repetition caused by failure or correction.
- [x] **HLTH-10**: Every health observation includes reason codes, evidence window, sample size or opportunity count, freshness, affected capability IDs, confidence, and a non-destructive remedy.
- [x] **HLTH-11**: Health thresholds, sample floors, decay, cooldown, and multilingual calibration remain versioned, testable, locally derived, and guarded by canary evidence.

### Advisory Stewardship Interface

- [x] **UX-01**: Startup remains silent unless one high-confidence, novel, actionable capability observation exists.
- [x] **UX-02**: A startup observation is compact, non-blocking, deduplicated, cooldown-controlled, and points to `/router suggestion` for details.
- [x] **UX-03**: `/router suggestion` returns exactly one prioritized actionable recommendation plus a compact overall capability-health overview.
- [x] **UX-04**: `/router suggestion` shows the recommendation’s evidence, confidence, affected capabilities, expected benefit, risk, and safe proposed next action.
- [x] **UX-05**: Users can inspect, dismiss, snooze, or correct a suggestion without mutating capability definitions or silently changing routing policy.
- [x] **UX-06**: Missing-capability remediation follows recommendation → explicit approval → draft → preview, and never installs the draft automatically.
- [x] **UX-07**: Draft previews show exact paths, semantic changes, dependencies, conflicts, representative before/after routes, verification steps, reversibility, and rollback implications.
- [x] **UX-08**: Router never automatically installs, deletes, disables, merges, archives, rewrites, activates, or publishes personal capabilities.
- [x] **UX-09**: Router adds no dashboard, timeline, per-session summary, unranked finding dump, or large family of maintenance commands.

### Deterministic Hot Path and Guarded Publication

- [x] **REL-01**: Prompt submission performs no filesystem discovery, manifest parsing, history analysis, usefulness calculation, graph traversal, mutation, network request, or additional model call.
- [x] **REL-02**: Background analysis compiles bounded contracts, relationships, intent rules, workflow transitions, local equivalents, and suggestion references into the existing read-only prompt index.
- [x] **REL-03**: The active registry, contracts, relationship graph, intent policy, workflow routes, health policy, and suggestion references publish as one version-consistent immutable tuple.
- [x] **REL-04**: Node, edge, dependency, adapter, inference-rule, manifest, correction, and negative-evidence changes invalidate all affected tuple members atomically.
- [x] **REL-05**: All routing-map changes pass the existing guarded verifier, publishing, canary, activation, last-known-good, rollback, and recovery processes.
- [x] **REL-06**: Existing skill, agent, command, workflow, MCP, and tool recommendations remain available and compatible after the v1.3 schema extension.
- [x] **REL-07**: Warm routing p95 remains below 25ms, every measured route remains below 100ms, and injected context remains within existing byte and token budgets.
- [x] **REL-08**: Full and incremental builds produce byte-identical outputs, and failed or partial background analysis cannot alter the active tuple.
- [x] **REL-09**: All automatic mutations remain behind explicit approval and existing safety gates, while recommendation-only and prompt-time failures preserve fail-open user interaction and last-known-good routing.

## Future Requirements

### Ecosystem Packaging

- **FUT-01**: Third parties can distribute trust-scoped adapter packages after adapter loading, signature, compatibility, and startup-cost contracts are proven.
- **FUT-02**: A stable external JSON Schema can standardize optional manifests after interoperability needs justify a public contract.

### Advanced Calibration

- **FUT-03**: Users can opt into broader multilingual calibration after local adversarial fixtures establish safe execution-polarity thresholds.
- **FUT-04**: Health analysis can adopt stronger ineffective-capability classifications after outcome semantics and exposure-aware thresholds are validated in practice.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Hosted service, shared telemetry, community analytics, or remote recommendations | Violates the fully local privacy boundary |
| Raw prompt, transcript, secret, source-document, or arbitrary tool-output retention | Unnecessary for bounded outcome analysis and creates privacy risk |
| Prompt-time LLM, embedding, vector database, network lookup, discovery, or health analysis | Violates deterministic latency, privacy, and offline behavior |
| Hard-coded GSD, Gstack, or ecosystem-specific workflow model | Personalized installations and normalized contracts are authoritative |
| Automatic installation, deletion, disabling, merging, archival, rewriting, activation, or publication | Probabilistic stewardship findings cannot grant mutation authority |
| Dashboard, timeline, per-session summary, or maintenance-command suite | The interface is intentionally quiet and centered on `/router suggestion` |
| Replacement of user-preferred frameworks | Router coordinates installed capabilities rather than imposing a framework |
| A second execution, publication, rollback, telemetry, or recommendation engine | v1.3 must extend the verified v1.2 control plane |
| Treating hooks as task-dispatch capabilities | Hooks remain bound to their declared lifecycle events |
| Cross-machine synchronization | Local authoritative state and privacy boundaries take priority in v1.3 |
