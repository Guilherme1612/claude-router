<objective>
Wave 2: close the post-work observation loop and add opportunity-aware usefulness scoring.

Plan 24-01 proved the schema + store + inspect tracer with one outcome_kind ('selected'). This plan extends observe.mjs to derive all 9 outcome_kind values (HLTH-03) by correlating telemetry records with workflow transition advancement + downstream invocation signals, off the hot path. It then adds score.mjs — a per-capability usefulness scorer that weights recency, reversibility, confidence, and opportunity exposure rather than frequency alone (HLTH-06), with an "unjudged" tier that protects rare and new capabilities from weak-evidence misclassification (HLTH-07).

Purpose: The router's v1 telemetry schema left `outcome: null` and `downstream_invocations: null` reserved but never populated (RESEARCH Summary). This plan populates the bounded outcome signal that closes that loop, in a form Phase 25's `/router suggestion` and Phase 26's health-policy tuple member can consume.

Output: src/health/observe.mjs (full), src/health/score.mjs, two test files. HLTH-03/06/07 green.

This is the conservative baseline the Deferred Items table explicitly endorses.

    Create src/health/score.mjs — a per-capability usefulness scorer. Analog: src/evolution/evidence.mjs computeWeightedSamples (lines 63-69) for the recency dimension; the confidence_basis_points 0..10000 bounding convention from src/registry/relationships.mjs.

    1. scoreCapability({ outcomes, contract, now=Date.now() }) where outcomes is an array of persisted outcome records for one capability_id and contract is the contract envelope (src/registry/contract.mjs buildCapabilityContract output) for that capability. Returns { capability_id, usefulness_basis_points, tier, sample_count, signal_breakdown, reason_codes }.

    2. tier (HLTH-07, D-1): if sample_count < MINIMUM_SAMPLES (imported from evidence.mjs — do NOT redefine), return tier='unjudged', usefulness_basis_points=null, reason_codes=['insufficient_samples']. No 'long_unused' or 'ineffective' reason_code is ever attached to an unjudged capability. This is the conservative baseline; the Deferred Items table explicitly defers deeper rare-role classification (recovery/incident/release/migration) to a future phase.

    3. Above the floor: compute usefulness_basis_points as a bounded weighted combination (0..10000):
       - recency_weight = computeWeightedSamples(outcomes, { now, halfLifeMs: HALF_LIFE_MS }) / sample_count (exponential half-life, imported)
       - completion_rate = count(outcome_kind='completed') / sample_count
       - opportunity_exposure = sample_count / (sample_count + count(outcome_kind='abandoned') + count('overridden')) — what fraction of opportunities this capability actually addressed
       - reversibility_factor = { 'reversible': 1.0, 'unknown': 0.7, 'irreversible': 0.4 }[contract.reversibility ?? 'unknown']
       - confidence_factor = (contract.confidence_basis_points ?? 5000) / 10000
       - penalty = count('corrected') + count('retried') + count('replaced') — failure-driven outcomes reduce the score
       - usefulness_basis_points = round(10000 * (0.30*recency_weight + 0.25*completion_rate + 0.20*opportunity_exposure + 0.15*reversibility_factor + 0.10*confidence_factor) * (1 - penalty/sample_count))
       Folding of actually_used and helpful_reuse (HLTH-06 wording): actually_used outcomes contribute to sample_count and recency (they count as evidence the capability was the one dispatched, so they enter computeWeightedSamples); helpful_reuse outcomes are also captured as 'completed' when the workflow advanced on the later prompt, contributing to completion_rate (a helpful_reuse record carries outcome_kind='helpful_reuse' AND is double-counted as completion-rate evidence via its route_id correlation with the advancing workflow). No separate weight is added for these two kinds — they flow through the existing dimensions (sample_count, recency, completion_rate) rather than a dedicated slot, so HLTH-06's "considers ... actually used ... helpful reuse" wording is satisfied visibly without gratuitous new weights.
       The weights are versioned in Plan 24-04's thresholds.mjs (POLICY_VERSION='health-policy-v1'); score.mjs imports them. For this wave, inline the defaults with a comment noting they move to thresholds.mjs in Wave 4.

    4. tier thresholds (versioned, canary-guarded in Wave 4): usefulness_basis_points >= 7500 → 'high'; >= 5000 → 'medium'; >= 2500 → 'low'; < 2500 → 'low_usefulness' (reason_code 'low_usefulness'). tier='unjudged' short-circuits before this mapping.

    5. signal_breakdown returns every input dimension: { recency_weight, completion_rate, opportunity_exposure, reversibility_factor, confidence_factor, penalty_count, outcome_kind_counts }. Every dimension is observable so Phase 25's suggestion surface can explain WHY a capability scored the way it did (HLTH-06 transparency).

    6. The scorer NEVER reads record.name or a framework-specific field. capability_id is the stable local id (Plan 24-01 invariant). The scorer NEVER runs on the UserPromptSubmit hot path — it is called only by the off-hot-path observer / admin inspect / Phase 25 suggestion surface.
